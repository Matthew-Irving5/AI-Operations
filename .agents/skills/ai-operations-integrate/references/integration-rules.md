# AI Operations integration rules (living architecture checklist)

Read only rows touching the current ticket. The IDs are stable; update a rule when implementation changes, preserving its evidence link. A ticket readback remains required but is not a substitute for these concrete integration conventions.

## Supabase / migrations / privileges

- **DB-01 — Execute as the real caller.** A Supabase `service_role` JWT does **not** grant arbitrary table INSERT/SELECT when explicit Postgres grants deny it. For prompt candidate creation, call the existing restricted `create_prompt_candidate` SECURITY DEFINER RPC; do not insert into `prompt_versions` directly or weaken its ACL. Extend existing RPCs and caller-role tests, not service privileges. (AI-16 PR #170, commit `170d537d`)
- **DB-02 — Protected tables are not a diagnostic API.** Direct PostgREST `service_role` SELECT on protected `trace_events` / `prompt_version_transitions` is intentionally denied (403/42501). Read via the authorized UI/query RPC; for prompt-transition replay, call `transition_prompt_version` with the exact original key, actor, operation and versions, then require `replayed: true`. That proves the keyed effect already exists; do not describe it as a directly observed table count. Never add SELECT grants solely to debug. (AI-16/19 staging 15/20 Oct; AI-44-10 below)
- **DB-03 — Shared migrations are one timeline.** Before creating migrations in a parallel worktree, inspect committed migrations on main AND active sibling PRs. Use a fresh unique version prefix; do not reuse `20261015210000`. Forward migrations only; never rewrite applied history. Resolve collisions before composing/deploying sibling PRs. (AI-16 `cde425bd`, AI-19 `5209bd10`)
- **DB-04 — Generated type parity is semantic and toolchain-pinned.** Schema drift checks must distinguish actual missing/changed columns/RPC signatures from Supabase CLI representation changes such as an inline `SetofOptions` row versus a referenced row array. Generate types with the exact Supabase CLI version in the root `pnpm-lock.yaml`; if the installed CLI differs, run `corepack pnpm install --frozen-lockfile` before generation. Do not hand-edit stored generated types to conceal real drift. (AI-19 staging run `39475753561`; AI-28 run `39644833934` and pinned-CLI parity)
- **DB-05 — Validate at every writing boundary.** Existing SQL write/commit procedures can enforce narrower rules than TypeScript or Edge validation. When adding a provider shape, inspect SQL validations and persisted schemas as well. Example: `commit_instrumented_ai_report` formerly demanded at least one report section while the governed provider schema allowed zero. (AI-16 `39e68b5`, `cde425b`)

## Edge / runtime / package boundaries

- **EDGE-03 — Keep paired-token issuer and Edge endpoint in the same environment.** A device token issued by the staging Supabase project must be sent to that project's function URL; onboarding instructions must identify environment-specific endpoints instead of reusing a production URL. Test the documented URL against the project configured by the pairing flow. (AI-28 `apps/web/app/api/apple-bridge/device/route.ts`, `docs/onboarding/apple-shortcuts.md`)
- **DB-09 — Reconcile the provider's full actual cost.** Keep the reservation amount as the held estimate, record actual provider consumption even when it exceeds that estimate, and release only the unused remainder. Update the relevant hard-cap total atomically with settlement; never clamp actual cost to the estimate or reject reconciliation after the provider has charged. (AI-20 PR evidence pending)
- **DB-12 — Keep per-call pricing and complete usage together.** Capture the immutable effective `model_pricing.id` during reservation; calculate the later provider actual against that exact row, including cache-write tokens. Reject incomplete or stale/unverified usage for reconciliation and record the failure for operator review; never silently use the latest price or treat a missing usage field as zero. Prove the reservation→webhook→settlement path and immutable-row ACL/trigger in local DB tests. (AI-20 PR #178; local reset and pgTAP)
- **DB-13 — Keep staging acceptance reads read-only and ACL-aware.** `service_role` is not an unrestricted PostgREST diagnostic identity: column-scoped grants can intentionally deny filters or settlement fields used by a test. For AI-20's correlated workflow and accounting proof, use the fixed Supabase Management API `/database/query/read-only` endpoint with a `database_read`-scoped staging PAT; do not use the broader `/database/query` route or rely on its optional `read_only` flag. Validate the complete response schema, and run the same query with reserved empty UUIDs before opening the headed browser or making a provider call. Keep the staging PAT in the Node runner, remove it from the browser process environment, and never widen application-role grants or use this path for protected trace tables. (AI-20 PR #178, `ai20-cost-runtime-staging.test.ts`; [read-only query API](https://supabase.com/docs/reference/api/v1-read-only-query))
- **DB-14 — Poll for accounting settlement, not only workflow status.** A workflow may become `succeeded` while its correlated AI call still has null response ID, actual cost, or token counts. Permit those fields to be null in intermediate read snapshots, but do not accept the run until the provider response, complete usage, report, notification decision, reservation, budget, and pricing row are all settled; then retain strict reconciliation assertions. (AI-20 staging run `40000834798`, run `5d81c716-17d5-4a2f-b77e-9ad2cbf33e56`; regression `ai20-cost-runtime-staging.test.ts`)
- **DB-07 — Preserve externally asserted constraint diagnostics.** When replacing a persisted constraint, keep its externally asserted name and diagnostic contract; retain exact SQLSTATE/message assertions in the lowest relevant pgTAP test. (AI-44, `supabase/tests/agent_runtime_contracts.sql`)
- **DB-08 — Include every deployed SECURITY DEFINER RPC in the ACL matrix.** Assert the exact role/grant tuple for each deployed RPC in the security matrix, and account for individually verified additions in the staging ACL fingerprint comparison. (AI-44, `supabase/tests/rpc_security.sql`, `supabase/tests/local_application_role_acl_parity.sql`)
- **DB-10 — Preserve canonical identity at SQL boundaries.** When a write RPC validates both normalized data and its immutable raw copy, apply the same documented compatibility normalization to identity fields before comparing them. For mobile adaptation replays, serialize by raw-record identity, retry only rejected provenance for the same adapter version, keep raw receipts immutable, and leave successful provenance as a no-op on replay. Verify one canonical row and one provenance row. (AI-28 `mobile_reminder_scope.sql`, `mobile_adapters.sql`, 72/72; AI28-07 below)
- **DB-11 — Carry the complete migration test baseline with already-applied sibling migrations.** When a candidate must include exact migration files already applied by a sibling staging release, carry their corresponding pgTAP fixtures, explicit `SECURITY DEFINER` RPC allowlist entries, staging ACL fingerprint exclusions, and generated database types too. Update fixtures to satisfy the new persisted contract (for scoped reminders, v2 payload plus an enabled list); keep the assertions for exact grants and successful retry behavior. Do not loosen authorization checks or claim schema parity while generated types remain stale. (AI-35, `mobile_adapters.sql`, `rpc_security.sql`, `local_application_role_acl_parity.sql`, `packages/db/src/database.types.ts`)

## Edge / runtime / package boundaries

- **EDGE-01 — Deployment import maps differ from shared typecheck.** A shared `supabase/functions/deno.json` used in local `deno check` does not automatically configure each deployed Edge Function. Register the affected function's `import_map` in `supabase/config.toml` (such as `feedback-submit`) when using `@ai-operations/*` aliases; prefer the repo's established per-function mapping. (AI-19 `ff1ee65b`, staging `39473033548`)
- **EDGE-02 — Keep workspace sources in QA staging.** Imports added across packages must be included in the existing `infrastructure/scripts/qa-workspace-dependencies.ts` staging of local test sources. A missing new package source can break Chromium test boot even when Edge typecheck passes. (AI-19 `ddf83218`, CI `38778271919`)
- **RUNTIME-01 — Cloudflare is not Next dev.** Relevant Worker routes and web runtime dependency updates must use the established OpenNext/Wrangler production-like preview. Keep Next, OpenNext and Wrangler compatible: Next 16.4 requires the adapter's real `preview-props.json` manifest support, never an empty-manifest fallback. `verify:changed` must route web package changes to Worker preview. Do not assume Next dev cookie/redirect/middleware behaviour is identical. Public origin must remain the browser's origin, not an internal `localhost` host. If auth isn't touched, do **not** introduce broad local MFA setup. (AI-16 `f9e40378`, `36fdcffc`; AI-44; upstream opennextjs/opennextjs-cloudflare#1356)
- **RUNTIME-02 — Match toolchain and runtime settings.** Invoke repository-pinned `corepack pnpm` (10.18.2 at incident time), not global pnpm 11; align local WSL/CI Node, generated OpenNext manifests and Worker build-vs-runtime variables. Prefer isolated targeted reproduction over committing CI-only guesses. (AI-16 `de04d023`, `aed1f0de`)
- **RUNTIME-03 — Parse actual CLI output, not guessed JSON substrings.** Supabase metadata CLI output may contain warnings/other JSON. Use stable machine-readable modes and a robust defined parse contract; test the Linux CI stdout shape. (AI-19 `f1ba2852` through `62ce7845`)
- **RUNTIME-04 — Disposable build copies must match current sources.** Serialize use of a shared WSL build copy. After validating its resolved disposable path and absence of Git metadata, synchronize with deletion of stale source files while preserving excluded dependencies and secrets. A previous branch's removed test must not enter the current build. (`wsl-worker-preview.sh`, `qa-workspace-dependencies.test.ts`)

## Mobile / device integration

- **UI-01 — Match empty success responses before parsing JSON.** Apple device revocation returns HTTP 204 through the Next proxy. Treat that documented status as an empty successful result; validate JSON objects for body-bearing responses. Never cast a failed JSON parse to an object and dereference it: the server can revoke successfully while the UI throws before confirmation/refresh. Test the actual 204 response and retained Google JSON details in the shared client parser. After asynchronous device creation, refresh the server-rendered inventory before locating the new card; register the exact revocation response waiter before the MFA handoff and await it before UI assertions. (AI-28 / AI28-12; `source-permissions.test.ts`, `live-auth-acceptance-harness.test.ts`)

- **MOBILE-01 — Pairing token and ingestion endpoint must share a Supabase project.** A mobile token is issued by the app's environment-configured Supabase project and is only valid at that project's `mobile-snapshot-ingest` endpoint. Never hardcode the production project URL into a staging Shortcut or setup guide. Keep the endpoint scoped to the paired environment and add a contract check that parses and compares the exact Supabase hostname and function path. (AI-28 PR #180, commits `d612f4c` and `91fb4d4`)
- **MOBILE-02 — Release bounded oversized request streams before returning from Supabase Edge.** When `Content-Length` proves a request exceeds the mobile transport cap, do not return while a near-limit body remains unread: Node `fetch` can see a 502 with no headers even while the Edge handler logs its intended 413. For a declared size no more than 64 KiB above the cap, stream and discard without buffering, stopping at EOF or canceling once actual bytes exceed the cap plus that fixed allowance. For larger declared sizes, cancel immediately. Keep the existing hard cap and correlated 413; never drain without a fixed bound. Cover the near-limit path, immediate cancellation, a lying length, and an at-limit untouched body, then prove status, error code, and correlation header through the real local Supabase Edge HTTP path. (AI-28 incident AI28-11; `_shared/mobile-request-limits_test.ts` and mobile Shortcut acceptance)
- **STG-01 — Preflight persistent staging migration history before deploy mutation.** A candidate for a persistent staging database must contain every migration version already applied there. Compare candidate files with staging's recorded versions through the read-only Supabase Management API before publishing deploy-pending status, deploying the Worker, or changing secrets; fail with the sorted missing version list so the candidate can be rebased onto the accepted migration history. After that preflight passes, use the pinned Supabase CLI's `db push --include-all` so intentionally earlier, unapplied migrations in the candidate are not omitted by timestamp filtering. Never repair applied staging history to make a behind candidate deploy: AI-35 run `39988529173` showed that a late `db push` can leave a new Worker deployed while schema application fails because versions `20261021155521`, `20261021155524`, and `20261022180901` are absent from the candidate checkout. Include their matching test baseline and generated types as required by DB-11. (AI-44 run `39786263958`; AI-39 migration `20261021131410`; AI-35 run `39988529173`; `environment-drift.test.ts`, `release-gate.test.ts`)

## Provider / orchestration / acceptance contracts

- **GITHUB-01 — Validate both requested and credential owners.** A fixed allowlisted repository URL does not prove that the caller-supplied target or configured token identity is approved. Reject injected owner aliases before rate-limit/MFA and GitHub work; verify the authenticated token with GitHub `/user`; only then construct repository URLs from the exact `Matthew-Irving5` owner. Treat `BrightSG` as a case-insensitive hard deny, audit only safe reason codes, and prove denied identities make zero repository calls. (AI-35 Career boundary regression)
- **GITHUB-02 — Preserve owner denials across authenticated proxies.** A web proxy may validate and forward only the documented owner-target shapes to the authenticated Edge parser so it can emit the safe denial audit before MFA/provider work; do not short-circuit those known denials at the proxy. Keep unknown fields rejected at the proxy and retain Edge validation as authoritative. (AI-35 staging run `39639201782`, follow-up on `3835c62`)
- **AI-01 — One provider-output contract, end to end.** Compare the _persisted_ JSON schema sent to Responses with the shared runtime validator, SQL commit constraints and fixtures. All allowed shapes must succeed end-to-end: `report_sections: []` and permitted ASCII section codes with uppercase letters must be canonicalised as designed. Reject truly disallowed input; never fabricate sections to silence errors. (AI-16 `39e68b5`, `cde425b`, AI-19 `eaee6c7f`)
- **AI-02 — Candidate and rollback are different valid request variants.** Build API request validators from existing model/budget policies and the actual rollback journey. The Systems weekly launch allows the specifically authorised Luna/$0.05 and Terra/$0.15 combinations (no search), not an accidental cross-pair; keep route/harness/SQL budget semantics aligned. (AI-19 `de0caeaf`)
- **ACC-01 — Acceptance proof is an interface.** Before staging, inspect suite/profile selector, browser-session reuse, artifact writer, strict validator and consumer. An `auth-browser` artifact and a targeted `promptGovernanceProof` cannot be silently interchanged or written to the same incompatible output. Use the established exact-head/lease mechanism; no ad hoc ephemeral helper stored under ignored test-results. Playwright clears its output directory at suite start: keep durable coordination state outside runner-owned output, and use a unique per-suite output subdirectory so one journey cannot delete sibling results. (AI-16/19 `cbe549bb`, `777184d1`)
- **ACC-02 — Human MFA is a genuine external gate.** Do not wait 300 seconds for sign-in before confirming the operator sees the current headed browser. Pause and ask for the action clearly; reuse the accepted auth context where possible. Skip complete local MFA for unaffected tickets. (AI-16/19 15/20 Oct)
- **ACC-03 — Authenticated shell journeys require hosted browser acceptance.** Candidate profile selection must account for the protected app shell and its authenticated platform journey, even when no auth endpoint changes. Changes to the shell layout/navigation or `tests/e2e/platform-authenticated.spec.ts` require the `auth-browser` profile; do not auto-accept a deployment-only smoke as a user-journey proof. (AI-22 PR #174, staging run `39614521311`)
- **ACC-04 — Ticket live proof outranks changed-path heuristics.** Read the issue's explicit hosted sign-off before dispatch and select the proof profile that matches the required boundary. Targeted auto-accept cannot satisfy a required operator journey, and generic `auth-browser` cannot stand in for a ticket-specific provider/device contract. Add a focused selector regression for the exact issue marker and a strict evidence check for the capability's required effect. (AI-44 PR #181, AI-41 PR #173, AI-35 PR #182, AI-28 PR #180)
- **ACC-05 — Let the ticket owner strengthen the hosted profile explicitly.** When issue-required proof is not represented by changed paths, allow the candidate dispatch to request the matching stronger profile; the override may strengthen inferred `targeted` but must never downgrade auth or replace a ticket-specific proof. For a candidate requiring both AI-28 mobile and AI-44 action acceptance, select the combined profile and retain both nested evidence envelopes. (AI-28 PR #180, AI-44 PR #181, `acceptance-profile.ts`, `release-gate.test.ts`)
- **ACC-07 — A ticket-specific acceptance needs its own runner and evidence contract.** Select the profile from the ticket readback marker, route only to its dedicated hosted spec, and keep the candidate pending until a strict evidence schema binds checks to the current deployment. The generic live suite proves only the journeys it actually runs; it cannot accept a ticket with no matching spec. (AI-39 PR #176, `run-live-e2e.ts`, `procurement-live-acceptance.ts`)
- **ACC-08 — Mobile pairing acceptance requires device-path evidence.** Pairing, valid and replayed uploads, changed-only adaptation, revoke/no-write, invalid/retry recovery, provenance, and freshness are separate checks; generic browser MFA/action evidence does not prove them. Record observed pairing and revocation MFA independently and require explicit operator confirmation of the actual Apple Shortcut run; synthetic HTTP transport alone is insufficient. For a candidate that also contains canonical action changes, require one strict envelope containing both exact-candidate mobile proof and fresh-MFA action/receipt proof, and keep each nested contract distinct. (AI-28 PR #180, AI-44 PR #181, `release-gate.ts`, `release-gate.test.ts`)
- **ACC-09 — Authenticated provider sync needs its provider-specific proof.** A generic authenticated browser suite cannot establish personal-account scope, actual sync, evidence ingestion, or owner-denial audit behavior. Route Career candidates to the dedicated Career runner and validate its redacted candidate-bound evidence envelope before acceptance. (AI-35 PR #182, `career-staging-acceptance-evidence.ts`)
- **ACC-10 — Match acceptance evidence to the exact consumer envelope.** A dedicated runner's flat profile evidence is input to the `staging-status` converter; `staging-accept` consumes only the candidate-bound wrapper with matching outer metadata and nested profile evidence. Test the intended conversion and reject passing the flat producer artifact directly to the later consumer. (AI-39 PR #176, `release-gate.ts`, `release-gate.test.ts`)

- **ACC-11 — Combined staging acceptance belongs to one PR tree.** A candidate-bound acceptance for a descendant PR cannot authorize its parent PR: main requires the staging status on the exact head, and production checks the accepted PR number and merge tree. Release a combined, fully proved candidate through its owning PR and close overlapping PRs as superseded after production smoke, or obtain independent acceptance for each separate merge. Never copy statuses between heads. (`release-gate.test.ts` squash-provenance regression; AI-28/44 PR #181)
- **ACC-12 — Headed Playwright worker confirmation must not assume a TTY.** Playwright workers may have non-TTY stdin/stdout even when their parent runner is attached to a visible terminal. For operator-only confirmation, accept a parent-written marker under ignored `test-results/` only after the actual external action is confirmed; bind it to the current candidate SHA/tree and observed device/snapshot IDs. Keep the interactive prompt as a fallback and reject stale or mismatched markers. (AI-28 staging run on candidate `0955d7c3137266ecf71edbff0d4a7c168e0409a3`; `mobile-shortcut-operator-confirmation.test.ts`)
- **OPS-02 — Serialize legacy shared local DB resets.** The default `ai-operations-local` database stack is shared across worktrees. Give `test:db` one explicit owner until completion; other lanes may run independent checks and isolated Chromium stacks. An isolated browser stack does not isolate the legacy DB test runner. Do not remove another lane's containers to resolve a duplicate-name error. (AI-39 duplicate `supabase_db_ai-operations-local`; serialized AI-44 DB proof passed)

- **ACC-06 — Cost-runtime acceptance has one canonical proof contract.** Route the AI-20 readback marker to its one-call hosted profile, keep the candidate pending until that bounded call passes, and validate producer output with the same `Ai20CostRuntimeProofSchema` used by the release gate. Bind a manual acceptance dispatch to the exact profile recorded in the candidate deployment. Record observed MFA explicitly, complete token usage and immutable pricing inputs; never auto-accept or treat the generic live suite as the cost proof. Keep profile tests and harness assertions scoped to their exact tag when several acceptance journeys share a spec file. Prove producer-to-hosted-validator conversion without another provider call. (AI-20 PR #178, `ai20-cost-runtime-proof.test.ts`, `release-gate.test.ts`, `live-auth-acceptance-harness.test.ts`)
- **OPS-01 — The failure message should give the cause, not just the stage.** Return the failed invariant, owning boundary/contract, expected versus actual and precise safe field/path. Never log passwords, PII, raw provider prompts or restricted trace tables to achieve diagnostic accuracy. (AI-16/19 staging investigations)

- **QA-02 — Probe before installing Linux browser OS dependencies in CI.** Install Playwright browser binaries separately, then launch each selected browser headlessly. Only run `playwright install-deps <browser>` when that launch reports missing shared libraries; keep `playwright install --with-deps` for fresh non-CI Linux hosts. This avoids waiting on apt when hosted runner images already have the browser libraries. Keep browser setup bounded and actual test timeouts unchanged. (AI-20 PR #178, boundary run `39989448812`; Ubuntu image `20261012.334.1`)

- **DB-15 — Match staging reads to the current explicit grant inventory.** A valid `service_role` JWT does not imply SELECT on every table or column, and an owner RLS policy does not grant browser access by itself. Use an authenticated owner's JWT only for projections listed in the current explicit ACL contract, such as `actions`, Apple bridge devices, and freshness. Read MFA freshness through the existing canonical action-context RPC instead of querying authentication events directly. The later blanket authenticated-table revoke in `20261008200132_explicit_service_only_table_access.sql` supersedes earlier typed-mobile SELECT grants; mobile snapshots, provenance, and typed canonical rows have no browser read grant and stay behind trusted RPC/Edge paths. For staging verification of their generated synthetic state, use the server-only Supabase management SQL endpoint with `read_only: true`, a fixed staging project ref, exact candidate metadata, a strict table/column/filter allowlist, and an explicit owner/device/synthetic-row scope; never expose the management token to browser code or add grants solely for tests. Check every runner query against the latest ACL migration before staging. (AI-44 and AI-28 staging 403s; `20261008200132_explicit_service_only_table_access.sql`; `tests/e2e-live/ai44-action-acceptance.spec.ts`, `tests/e2e-live/mobile-shortcuts-acceptance.spec.ts`; AI44-10, AI28-08, AI28-10 below)
